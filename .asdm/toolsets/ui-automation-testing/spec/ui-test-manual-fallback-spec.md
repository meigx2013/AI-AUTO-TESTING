# 人工兜底流程规范

## 概述

本规范定义了方案 v1.1 第 8 章「人工兜底流程」的标准：当 AI 无法自动完成测试脚本的生成、执行或自愈时，向测试人员输出结构化的兜底清单，并将人工处理结果回流脚本库。

## 触发条件

满足以下任一条件即触发人工兜底：

| 来源指令 | 触发条件 |
|---------|---------|
| 执行指令（`/asdm-ui-test-run`） | 脚本执行失败（v1.0：失败即转人工） |
| 保鲜指令（`/asdm-ui-test-freshness`） | AI 自愈失败，或同一脚本自愈连续失败达到阈值（2 次） |
| 设计与编码指令（`/asdm-ui-test-design-generate`） | 任务清单存在定位缺失（❌/⚠️）且未补录 |

## 兜底流程

1. **输出兜底清单**：系统按模板输出问题脚本、报错原因、AI 已尝试的修复动作
2. **人工处理**：测试人员介入 —— 修复脚本、补录 recorder json、或更新数据文件
3. **结果回流**：处理结果回流脚本库，并记录原因，沉淀为标注/知识，供后续 AI 参考
4. **重新验证**：必要时重新触发相应指令验证（执行指令 / 保鲜指令 / 设计与编码指令）

## 兜底清单模板

兜底清单作为执行报告（`report.md`）、保鲜报告（`freshness-report-*.md`）或定位缺失反馈中的一个章节输出：

```markdown
## 转人工清单

| 序号 | 问题脚本 | 所属场景 | 报错原因 | AI 已尝试的修复动作 | 建议人工操作 |
|------|---------|---------|---------|--------------------|-------------|
| 1 | `<脚本路径>` | <场景编号> | <从错误日志提取的关键原因> | <动作摘要，如"自愈 2 次：更换 aria 选择器 → 更换 CSS 选择器，均失败"；无则填"—"> | <具体建议，见下表> |

### 人工操作指引

<针对每项的具体操作步骤，如：>

1. **补录录制脚本 - <环节名>**
   - 使用 Chrome Dev Tools Recorder 录制该环节完整操作
   - 导出 json 归档至 `recordings/<模块>/<模块>-<场景简称>.json`
   - 重新触发 `/asdm-ui-test-design-generate`

2. **修复脚本 - <场景名>**
   - 检查 `<脚本路径>` 第 <n> 步（stepId: `<stepId>`）
   - 参考 `annotations.json` 中该步骤描述：<描述>
   - 修复后重新触发 `/asdm-ui-test-run <用例文件夹>`
```

### 建议人工操作类型

| 类型 | 适用情况 | 操作要点 |
|------|---------|---------|
| 补录 recorder | 定位缺失、环节无脚本覆盖 | Chrome Dev Tools Recorder 录制 → 导出 json → 归档 `recordings/<模块>/` → 重新触发设计与编码指令 |
| 修复脚本 | 自愈失败、断言失败 | 按兜底清单定位 stepId，参考 annotations.json 描述手动修复 |
| 更新数据 | 账号失效、环境变更 | 更新用例文件夹下 `data/` 数据文件（见 `ui-test-data-spec.md`） |
| 确认变更 | 需求变更导致脚本语义过期 | 审阅 AI 变更 diff 摘要，确认后入库 |

## 回流规范

人工处理完成后，必须将处理结果回流，沉淀为后续 AI 可参考的知识：

1. **脚本修复**：修复后的脚本覆盖入库（同一用例文件夹路径），保留 `# @healed <日期>: <修改说明>` 注释记录修复原因
2. **补录归档**：新录制 json 归档至 `recordings/<模块>/`，文件名与缺失环节对应
3. **标注更新**：人工修复中发现的语义信息（如"该按钮文案已改为 XX"）同步更新 `annotations.json` 对应 stepId 的描述
4. **原因记录**：在兜底清单中回填「人工处理结果」列：处理方式 + 原因 + 日期，作为历史知识保留在报告文件中
