## Description
快速记录一个新特性的想法。用户只需提供新特性的基本思路，AI 进行语义分析后，按特性模板编写概述部分，创建对应的特性文件夹，并将新特性条目插入到 `ASDM-ProductPlanning.md` 的特性列表2（规划中）顶部。

本 action 适用于**早期想法捕捉**场景——当团队产生新特性想法但尚未进入正式规划流程时，用最轻量的方式记录想法、分配编号、创建初始文档，避免灵感流失。后续可通过 `/asdm-feature-planning` 或 `/asdm-feature-planning-lite` 进行深度规划。

**与其他 action 的区别**：

| 维度 | `asdm-feature-idea` | `asdm-feature-planning-lite` | `asdm-feature-planning` |
|------|:-------------------:|:---------------------------:|:----------------------:|
| 目的 | 快速记录想法 | 轻量规划 | 完整规划 |
| 代码扫描 | ❌ 不执行 | ✅ 两阶段扫描 | ✅ 两阶段扫描 |
| 文档深度 | 仅概述部分 | 6 章精简文档 | 14 章完整文档 |
| 适用场景 | 想法捕捉、灵感记录 | 中小特性快速规划 | 大型特性深度规划 |
| 后续衔接 | → `/asdm-feature-planning-lite` 或 `/asdm-feature-planning` | 直接进入实现 | 直接进入实现 |

## Usage
```
/asdm-feature-idea <自然语言描述>
```

用户可以用自然语言描述新特性的基本思路，AI 将自动提取所需参数。如缺少必要信息，AI 会向用户询问确认。

## Parameters

所有参数均可通过自然语言输入，AI 自动提取。若必填参数缺失，AI 须向用户询问。

| 参数 | 必填 | 说明 | 示例 |
|------|:----:|------|------|
| `name` | ✅ | 特性名称 | "MCP 注册表"、"用户个人令牌" |
| `module` | ✅ | 归属模块编号（参考 ASDM-ProductPlanning.md 模块清单） | 4（资源库管理）、13（MCP Hosting） |
| `description` | ✅ | 特性简要描述（用户的基本思路） | "补齐 MCP 注册表同步、公开 API 和前端管理页面" |
| `priority` | ❌ | 优先级 P1/P2/P3（默认：P2） | P1 |
| `release` | ❌ | 目标发布版本 | R05、R06 |
| `depends` | ❌ | 依赖的特性编号，逗号分隔 | FT-003、FT-003,FT-019 |

## Examples

### 自然语言输入
```
/asdm-feature-idea 想给平台加个通知中心，用户能收到系统消息和协作通知，P2 优先级
```

```
/asdm-feature-idea MCP Hosting 需要一个访问控制功能，和认证系统集成，提供 API Key 管理，依赖 FT-003 用户个人令牌
```

```
/asdm-feature-idea 想法：为工作区添加模板功能，用户可以保存和复用工作区配置，归属于模块5
```

## Process

### 1. 解析输入

从自然语言中提取参数：
- **特性名称**：从描述中提取或归纳特性名称（2-20 字符，简明扼要）
- **模块编号**：从描述中提取或推断归属模块
- **特性描述**：提取用户的核心思路，进行语义分析和整理
- **优先级**：语义映射（"高优先级"/"紧急"→P1，"低优先级"→P3）
- **Release**：匹配 "R\\d+" 格式或语义（"下个版本"需确认）
- **依赖**：匹配 "FT-\\d{3}" 格式，或语义（"依赖xxx"→查找对应特性编号）

若无法确定特性名称或模块编号，向用户询问确认。

### 2. 语义分析与整理

对用户提供的特性思路进行语义分析：
- **核心问题识别**：用户想要解决什么问题？
- **价值归纳**：这个特性能带来什么价值？
- **范围界定**：特性的影响范围大致覆盖哪些模块和功能？
- **关联发现**：与现有特性的关联和依赖关系

### 3. 参数校验

- 校验模块编号是否在 `ASDM-ProductPlanning.md` 模块清单中
- 校验特性名称不与现有特性重复
- 校验依赖的特性编号存在
- 将用户模糊描述映射到具体模块编号（如"认证模块"→1、"资源库"→4）

### 4. 生成待澄清问题清单

基于语义分析的结果，识别用户描述中的模糊点、缺失信息和潜在歧义，生成待澄清问题清单。

**问题生成维度**：

| 维度 | 说明 | 示例问题 |
|------|------|----------|
| 目标明确性 | 特性要解决的核心问题是否清晰 | "通知中心主要解决什么问题？是实时推送还是定期汇总？" |
| 范围边界 | 特性的影响范围和边界是否明确 | "通知是否包含系统告警？还是仅限协作消息？" |
| 用户角色 | 目标用户和使用场景是否清晰 | "通知中心面向哪些角色？所有用户还是仅管理员？" |
| 数据来源 | 特性涉及的数据来源和类型 | "系统消息和协作通知分别来自哪些模块？" |
| 交互方式 | 用户与特性的交互方式 | "用户如何查看通知？站内信、弹窗、还是邮件？" |
| 依赖关系 | 与其他特性的关联是否明确 | "是否需要与 FT-003 用户个人令牌集成？" |
| 技术约束 | 是否有特殊的技术要求或限制 | "是否有实时性要求？是否需要支持离线消息？" |

**生成规则**：
- 问题数量控制在 **3-7 个**，聚焦最关键的澄清点
- 每个问题必须具体、可回答，避免过于宽泛
- 问题按重要性排序：目标/范围 > 用户角色 > 数据/交互 > 依赖/约束
- 对于用户描述中已明确的内容，不再生成澄清问题
- 编号格式：`Q1, Q2, Q3, ...`

### 5. 分配编号与创建目录

1. 读取 `ASDM-ProductPlanning.md`，确定下一个可用 FT-XXX 编号（顺序递增，自动跳过已使用的编号）
2. 创建特性目录：`docs/planning/Feat/FT-XXX-{name}/`

### 6. 编写特性文档（仅概述部分）

基于语义分析结果，按特性模板编写概述部分到 `docs/planning/Feat/FT-XXX-{name}/FT-XXX-{name}-idea.md`。

- 想法阶段文档文件名使用 `-idea.md` 后缀（非 `-Feature.md`），后续通过 planning action 生成正式 `-Feature.md` 文档

- 修订记录中内容标注为"初始想法记录"
- 文档状态标注为"💡 想法记录"
- 核心价值基于用户思路进行语义扩展，通常归纳 2-3 条

### 7. 粗体格式检查（必须执行）

**写入文件前必须执行粗体格式检查**，按照 `specs4shared.md` 9.4 节的规范逐项检查 B1-B5：
1. 扫描文档中所有 `**...**` 粗体标记
2. 逐项检查 B1-B5
3. 自动修复发现的问题
4. 在输出中报告检查结果

### 8. 更新 ASDM-ProductPlanning.md（必须执行）

在 `ASDM-ProductPlanning.md` 的"特性列表2 - 规划中"中**顶部**新增条目：

```markdown
| FT-XXX | [{特性名称}](./Feat/FT-XXX-{name}/FT-XXX-{name}-idea.md) | {priority} | 🔵 规划中 | {特性说明} |
```

**插入位置**：特性列表2 表格的第一行（表头之后），确保新想法在最前面，便于团队快速看到最新记录。

### 9. 写入文档文件（必须执行）

**每次执行后必须将文档写入文件系统**，不得仅在对话中输出。

- 创建目录（如不存在）：`docs/planning/Feat/FT-XXX-{name}/`
- 写入想法文档：`FT-XXX-{name}-idea.md`
- 更新 `ASDM-ProductPlanning.md` 特性列表2
- 返回写入结果

### 10. 交互式澄清（必须执行）

文档写入完成后，向用户展示待澄清问题清单，引导用户逐一回答。

文档写入完成后，向用户展示待澄清问题清单，引导用户逐一回答。

**展示格式**：

```
📝 特性 FT-XXX「{特性名称}」已创建！以下是待澄清的问题：

Q1. {问题1}
Q2. {问题2}
Q3. {问题3}

请逐一回答上述问题（可直接按编号回复，如 "Q1: ..."），也可以一次性回答所有问题。
如暂不回答，可直接结束——问题会保留在文档中，后续可通过 /asdm-feature-planning-lite 或 /asdm-feature-planning 继续完善。
```

**澄清交互规则**：

1. **逐一引导**：用户每回答一个问题，AI 立即处理该回答：
   - 将回答内容写入文档对应问题的"澄清记录"列
   - 将问题状态从 🔲 待澄清 → ✅ 已澄清
   - 更新文档修订记录（新增一条"澄清 Q1-QN"记录，版本号递增 0.0.1）
   - 使用 `replace_in_file` 工具更新文档文件

2. **批量回答**：用户一次性回答多个问题时，批量处理所有回答，一次性更新文档。

3. **跳过处理**：用户表示暂不回答或想结束对话时，不强制追问，保留问题为待澄清状态。

4. **衍生问题**：用户回答中引入新的模糊点时，可追加新的澄清问题（编号继续递增），但追加数量不超过 2 个。

5. **澄清完成判断**：所有问题状态为 ✅ 已澄清，或用户明确表示结束澄清时，进入完成阶段。

**文档更新模板（待澄清问题部分更新后）**：

```markdown
### 待澄清问题

> 以下问题基于当前想法描述中的模糊点生成，请在后续对话中逐一澄清。澄清后文档将自动更新。

| 编号 | 问题 | 维度 | 状态 | 澄清记录 |
|:----:|------|------|:----:|----------|
| Q1 | {问题} | {维度} | ✅ 已澄清 | {用户回答摘要} |
| Q2 | {问题} | {维度} | 🔲 待澄清 | |
| Q3 | {问题} | {维度} | ✅ 已澄清 | {用户回答摘要} |
```

### 参数提取规则

AI 应从自然语言中智能提取以下信息：

- **特性名称**：从描述中提取核心概念，归纳为 2-20 字符的简短名称
- **模块编号/名称**：
  - 数字（如"模块4"、"4"）→ 直接映射
  - 名称关键词（如"认证"、"资源库"、"MCP Hosting"）→ 查找模块清单映射
  - 若无法确定，向用户确认
- **优先级**：匹配 "P1"/"P2"/"P3" 或语义（"高优先级"→P1，"低优先级"→P3，默认 P2）
- **Release**：匹配 "R\\d+" 格式或语义（"下个版本"需确认）
- **依赖**：匹配 "FT-\\d{3}" 格式，或语义（"依赖xxx"→查找对应特性编号）
- **特性描述**：剩余的自然语言内容

### 缺失参数确认

当必填参数缺失时，AI 应一次性列出所有缺失项向用户确认，格式示例：

```
请补充以下必要信息：
1. 特性名称：请提供特性的简短名称（2-20字符）
2. 归属模块：请指定特性归属的模块（可选：1-认证与用户管理、4-资源库管理、13-MCP Hosting ...）
3. 特性描述：请简要描述特性的目标和思路
```
