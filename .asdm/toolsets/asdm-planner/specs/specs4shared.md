# Shared Specifications for ASDM Planner

> 本文档定义 asdm-planner 所有操作共享的规范，包括数据校验规则、路径约束和可靠性规则。

---

## 一、关键文档引用

| 文档 | 路径 | 用途 |
|------|------|------|
| 产品规划总览 | `docs/planning/ASDM-ProductPlanning.md` | 模块定义（编号1-14）、特性清单、编号分配、状态流转 |
| 特性文档模板 | `specs/templates/Feature-Template.md` | 特性文档标准结构和填写说明 |
| 进展报告模板 | `specs/templates/Progress-Report-Template.md` | 进展报告标准结构和填写说明 |

## 二、数据校验规则

### 2.1 特性编号 (Feature ID)

- 格式：`FT-XXX`（三位数字，左补零）
- 编号顺序递增，自动跳过已使用的编号
- 示例：FT-003、FT-040、FT-099

### 2.2 模块 (Module)

- 编号范围：1-14（以 `ASDM-ProductPlanning.md` 模块清单为准）
- 名称与编号的映射关系以规划文档中的"功能模块概述"表为准

### 2.3 优先级 (Priority)

- 有效值：P1（高）、P2（中）、P3（低）

### 2.4 状态 (Status)

- 有效值：🔵 规划中、🟠 设计中、🟡 实现中、✅ 已实现、❌ 已废弃
- 状态流转：规划中 → 设计中 → 实现中 → 已实现（任意阶段可废弃）

### 2.5 发布版本 (Release)

- 格式：`RXX`（如 R03、R04）
- P1 特性建议有明确的目标 Release

### 2.6 依赖关系 (Dependency)

- 前置依赖的特性编号必须已存在于 `ASDM-ProductPlanning.md` 特性清单中
- 被依赖的特性不得为"已废弃"状态
- 依赖关系不得形成环路

## 三、路径约束

### 3.1 特性文档路径

| 类型 | 路径 |
|------|------|
| 目录 | `docs/planning/Feat/FT-XXX-{特性名称}/` |
| 调研总结（每代码库一个） | `FT-XXX-{特性名称}-CodeResearch-{代码库名}.md` |
| 想法文档 | `FT-XXX-{特性名称}-idea.md` |
| 特性文档 | `FT-XXX-{特性名称}-Feature.md` |
| 调研总结完整路径 | `docs/planning/Feat/FT-XXX-{特性名称}/FT-XXX-{特性名称}-CodeResearch-{代码库名}.md` |
| 想法文档完整路径 | `docs/planning/Feat/FT-XXX-{特性名称}/FT-XXX-{特性名称}-idea.md` |
| 特性文档完整路径 | `docs/planning/Feat/FT-XXX-{特性名称}/FT-XXX-{特性名称}-Feature.md` |

> **说明**：涉及多个代码库时，每个代码库对应一个独立的调研总结文件。`{代码库名}` 为代码库目录名（如 `asdm-admin`、`asdm-agentorbit`）。
>
> **文档后缀规则**：想法阶段使用 `-idea.md` 后缀（标题格式 `# FT-XXX {特性名称}（想法）`），进入正式规划后生成 `-Feature.md` 后缀的正式文档。

### 3.2 进展报告路径

| 类型 | 路径 |
|------|------|
| 目录 | `docs/planning/Feat/FT-XXX-{特性名称}/` |
| 文件 | `FT-XXX-{特性名称}-特性实现进展报告.md` |
| 完整路径 | `docs/planning/Feat/FT-XXX-{特性名称}/FT-XXX-{特性名称}-特性实现进展报告.md` |

### 3.3 产品规划文档链接格式

在 `ASDM-ProductPlanning.md` 特性清单中，特性名称列必须包含指向对应特性文档的 Markdown 链接：

- 想法阶段格式：`[特性名称](./Feat/FT-XXX-{特性名称}/FT-XXX-{特性名称}-idea.md)`
- 正式规划格式：`[特性名称](./Feat/FT-XXX-{特性名称}/FT-XXX-{特性名称}-Feature.md)`
- 路径相对于 `ASDM-ProductPlanning.md` 所在目录（即 `docs/planning/`）
- 特性文档创建后，必须确保 `ASDM-ProductPlanning.md` 中的对应条目已更新为链接格式
- 进入正式规划后，需将链接从 `-idea.md` 更新为 `-Feature.md`
- 示例：`[用户个人令牌](./Feat/FT-003-用户个人令牌/FT-003-用户个人令牌-Feature.md)`

### 3.4 代码文件链接格式

所有特性文档中的代码文件链接必须使用可点击的 Markdown 链接格式：

- 使用相对路径，相对于当前文档所在目录
- 格式：`[描述文本](相对路径)`
- 路径必须正确指向实际存在的文件
- 示例：
  ```markdown
  - [特性模板](../templates/Feature-Template.md)
  - [产品规划](../../../../ASDM-ProductPlanning.md)
  - [FT-005 多库资源管理Git存储](./../FT-005-多库资源管理Git存储/FT-005-多库资源管理Git存储-Feature.md)
  - [AssetRepositoryService.java](asdm-admin/asdm-admin-services/.../service/repo/AssetRepositoryService.java)
  ```

### 3.5 根路径约束

所有路径相对于工作区根目录 `{WORKSPACE_ROOT}/`，具体路径由 LLM 根据实际工作区确定。

### 3.6 代码路径示例（asdm-admin）

```
asdm-admin/
├── asdm-admin-services/
│   └── asdm-admin-services-core/
│       └── src/main/java/ai/asdm/admin/core/
│           ├── entity/
│           ├── service/
│           ├── controller/
│           └── dto/
├── deploy/mysql/migrations/
└── web/src/
```

## 四、可靠性规则

### 4.1 文档操作

- 生成或修改文档前必须校验目标路径，避免意外覆盖（除非用户明确确认）
- `ASDM-ProductPlanning.md` 更新必须是原子操作
- 操作失败时不得产生部分写入的文件

### 4.2 代码扫描

- 文档内容必须基于实际代码扫描结果，不可凭空编造
- 发现歧义时必须向用户确认，不可基于推测编写文档

### 4.3 代码扫描要求（两阶段模式，多代码库逐库扫描）

特性规划采用两阶段模式，代码扫描在**阶段一（调研阶段）**完成，产出调研总结文件供**阶段二（正式规划阶段）**使用。**涉及多个代码库时，逐库扫描并撰写独立调研总结文件**。

1. 根据特性描述和归属模块，确定需要扫描的代码库清单
2. 向用户展示扫描计划，确认代码库清单无遗漏
3. 对清单中的**每个代码库**，依次执行以下步骤（一次只扫描一个代码库，完成后再扫描下一个）：
   a. 使用 code-explorer 扫描当前代码库，覆盖：
      - 代码库的目录结构和文件组织
      - 与特性描述相关的现有实现（API 端点、Service 层、Controller、前端组件、配置等）
      - 数据库 migration 脚本和数据模型定义
      - 配置文件、环境变量和基础设施定义
      - 与其他代码库的交互接口（API 调用、事件、共享类型等）
   b. 将扫描结果整理为结构化的调研总结文件，写入 `docs/planning/Feat/FT-XXX-{name}/FT-XXX-{name}-CodeResearch-{repo-name}.md`
   c. 单个代码库的调研总结文件内容包括：
      - 代码库名称和路径
      - 目录结构和关键文件列表
      - 现有实现分析（API 端点、Service 层、数据模型、前端组件等）
      - 关键发现和缺失项（编号格式：`{repo简称}-G1, {repo简称}-G2, ...`，确保跨库编号不冲突）
      - 与其他代码库的交互接口
      - 待确认问题清单（如有）
   d. 当前代码库扫描完成后，向用户简要汇报进度（已完成 X/Y 个代码库），继续扫描下一个
4. **歧义澄清**：如扫描中发现任何不清晰的部分，**必须向用户提出问题确认**，包括但不限于：
   - 模块边界模糊（特性影响范围不确定）
   - 代码逻辑不明（现有实现与预期不一致）
   - 依赖关系不确定（跨模块调用链不清晰）
   - 数据流向不明确（数据在模块间的流转路径）
5. **阶段一完成后**：所有代码库扫描完成后，提示用户创建新会话，在新会话中再次执行命令进入阶段二
6. **阶段二启动时**：校验所有调研总结文件是否完整——如存在缺失代码库则仅扫描缺失的代码库，如部分调研不完整则报告缺失项

## 五、状态标记规范

### 5.1 代码状态标记

| 标记 | 含义 | 使用场景 |
|:----:|------|----------|
| ✅ | 已实现 | 功能完整，代码已在主分支或特性分支 |
| ⚠️ | 部分实现 | 功能已编写但存在关键缺失 |
| ❌ | 未实现 | 功能完全不存在 |
| 🔲 | 待实现/待新增 | 计划中的功能，尚未编写代码 |
| ➡️ | 已拆分/已转移 | 功能已拆分到其他特性 |

### 5.2 优先级标记

| 标记 | 含义 |
|:----:|------|
| P0 | 必须完成，阻塞核心功能 |
| P1 | 应该完成，影响用户体验 |
| P2 | 可以延后，影响安全性或完整性 |
| P3 | 未来考虑，不影响当前版本 |

### 5.3 DoD 状态标记

| 状态 | 含义 |
|------|------|
| **已完成** | 该功能点已实现，无需额外开发 |
| **部分完成** | 该功能点部分实现，需进一步完善 |
| **待实现** | 该功能点尚未实现，需要在开发阶段实现 |

## 六、完成规范 (DoD) 格式

> DoD 是特性开发的验收标准，每个特性文档必须包含"完成规范"章节。

### 6.1 章节结构

```markdown
## X. 完成规范 (DoD)

> **状态说明**：
> - **已完成**：✅ 该功能点已实现，无需额外开发
> - **部分完成**：🟡 该功能点部分实现，需进一步完善
> - **待实现**：❌ 该功能点尚未实现，需要在开发阶段实现

### X.1 核心功能

| 编号 | 完成点 | 说明 | 状态 | 完成状态说明 |
|------|--------|------|------|------------|
| X.1.1 | 功能点名称 | 功能点描述 | 状态 | 当前实现情况说明 |

### X.2 数据一致性
...
```

### 6.2 完成点分类建议

| 分类 | 说明 | 适用场景 |
|------|------|----------|
| **核心功能** | 业务功能实现、数据处理、核心逻辑 | 所有特性必选 |
| **数据一致性** | 事务完整性、数据校验、冲突处理 | 涉及数据存储、处理的特性 |
| **用户体验** | 界面一致性、响应速度、错误提示 | 涉及用户交互的特性 |
| **安全性** | 权限控制、数据隔离、审计日志 | 涉及敏感数据、权限管理的特性 |
| **兼容性** | 前后兼容、API 兼容、数据迁移 | 涉及接口、版本升级的特性 |

## 七、修订记录格式

### 7.1 格式要求

修订记录用于追踪文档的历史变更，位于文档开头的"修订记录"章节。

```markdown
## 修订记录

| 版本 | 日期 | 修订人 | 修订内容 |
|------|------|--------|----------|
| 1.0.1 | 2026-04-18 | CodeBuddy | 更新特性名称为"XXX"，明确实现范围 |
| 1.0.0 | 2026-04-17 | CodeBuddy | 初始版本，基于已实现代码生成 |
```

### 7.2 格式说明

- 表头：`| 版本 | 日期 | 修订人 | 修订内容 |`
- 版本号格式：`X.X` 或 `X.X.X`（如 1.0、1.5、2.0）
- 日期格式：`YYYY-MM-DD`
- 新增修订记录时，添加到表格顶部（最新版本在前）
- **同一天的多次修订必须聚合为一条记录**，用分号分隔各项改动内容，版本号取当日最终版本
- **修订内容应简练**：每项改动用短语概括（不超过 10 字），省略具体章节号和细节描述；聚合后整条修订内容不超过 60 字
- 聚合示例：`1.5 | 2026-04-26 | Lei Xu | 重组文档结构；新增领域设计；精简文件结构`
- **修订人获取方式**：通过执行 `git config user.name` 检测当前 git 用户名，将结果填入修订人字段

### 7.3 版本号递增规则

- 补丁版本（第三位）：小幅修正、格式调整、链接更新
- 次版本（第二位）：新增功能、较大变更
- 主版本（第一位）：重大架构变更（较少使用）

## 八、章节编写要点

### 8.1 功能概述

- 第一段用 2-3 句话说明特性目标、范围和与其他特性的关系
- 核心价值用 **3-5 个要点**，每个要点以 **关键词加粗** 开头
- 核心价值应从用户视角描述价值，不是技术实现描述

### 8.2 完成规范 (DoD)

> 状态说明：
> - **已完成**：✅ 该功能点已实现，无需额外开发
> - **部分完成**：🟡 该功能点部分实现，需进一步完善
> - **待实现**：❌ 该功能点尚未实现，需要在开发阶段实现

### 8.3 现有代码分析

- **必须基于实际代码分析**，不可凭空编造
- 每个模块用表格列出文件、类名、状态、说明
- 代码库路径用 `> 引用格式` 标注
- 关键缺失项（G1, G2, ...）编号连续，后续章节可引用

### 8.4 使用场景

- 每个场景用编号列表描述操作步骤
- 场景应覆盖不同用户角色和使用方式
- 标注哪些步骤已实现、哪些待实现
- **使用文字描述，不使用代码块包裹操作步骤**

### 8.5 系统架构

- **使用文字描述系统架构**，说明各组件的关系和数据流向
- 可使用 **ASCII 图表** 展示架构关系（推荐，无需特殊解析器，便于在代码环境中直接阅读）
- **文件结构仅描述模块/包级别的变更摘要**，不列出具体类文件和内部目录结构
- 具体的技术决策（类名、文件组织、内部包结构等）由开发人员在实现阶段自行决定
- 特性文档只需确保变更摘要覆盖所有需求内容，不需要规定实现细节
- 推荐使用**变更摘要表**替代文件树结构，包含：变更模块、变更类型（新增/修改/删除）、功能说明、关联需求编号

**禁止在文件结构中列出的内容**：

| 禁止内容 | 原因 |
|----------|------|
| 具体类文件名（如 `ProcessDomain.java`） | 属于实现细节，由开发人员决定 |
| 内部包结构（如 `domain/workitem/`） | 属于实现细节，由开发人员决定 |
| 方法级别描述（如 `register()`/`execute()`） | 属于接口设计，已在 API 端点章节覆盖 |

**推荐替代方案**：

```markdown
### X.X 变更摘要

> 具体的文件组织、类名、包结构等技术决策由开发人员在实现阶段自行决定，以下仅列出需要新增或修改的功能模块和变更范围。

| 变更模块 | 变更类型 | 功能说明 | 关联需求 |
|----------|:--------:|----------|----------|
| 统一领域模型 | 🔲 新增 | 过程领域枚举、统一类型/状态/优先级模型 | A-2.1.1 |
| 适配器契约与注册 | 🔲 新增 | 适配器接口、注册表、域能力声明 | A-2.1.2 |
```

- 每行标注状态：✅ 已有文件、⚠️ 部分实现、❌ 未实现、🔲 待新增/待修改

### 8.6 接口设计

- REST API 用标准表格列出（HTTP方法、路径、功能说明）
- **请求体和响应使用表格描述字段**，不使用 JSON 代码示例
- 请求体字段表格包含：字段名、类型、是否必填、校验规则、说明
- 响应字段表格包含：字段名、类型、说明
- CLI 命令用表格列出参数和说明

### 8.7 领域特定章节（可选）

- 章节标题根据特性内容自定义
- 常见标题：令牌存储方案 / 认证流程详解 / 状态管理设计 / 数据同步方案
- 包含设计原则、当前实现、目标方案、详细设计
- **使用文字描述，不使用代码示例展示实现细节**

### 8.8 依赖关系

- 前置依赖：本特性依赖的其他特性
- 后续依赖：依赖本特性的其他特性
- 代码库依赖：涉及的代码库和路径
- 第三方依赖：需要安装的 npm/Maven 包

### 8.9 数据模型

- 当前数据结构和升级后数据结构分开描述
- **使用表格描述数据结构**，不使用 JSON 代码示例
- 数据库表用标准表格（字段、类型、约束、说明）
- **使用 ASCII 图展示表关系**（推荐，无需特殊解析器，便于在代码环境中直接阅读）
- 索引信息使用表格列出（索引名、字段、类型）

### 8.10 实现计划

- 先写阶段划分总表（阶段、内容、优先级、预估工时、交付物）
- 每个阶段用详细任务表格展开（任务、变更模块、说明、预估）
- 任务表格不包含具体文件路径列，文件组织由开发人员自行决定
- 预估工时用 **h（小时）或 d（天）** 为单位
- 每个阶段包含"集成测试"行

### 8.11 测试计划

- 分功能测试、安全测试、兼容性测试三节
- 功能测试表格包含：用例名、前置条件、操作步骤、预期结果
- 安全测试和兼容性测试表格可适当简化

### 8.12 风险与缓解

- 编号用 R1, R2, ... 连续
- 每个风险包含：风险描述、概率、影响、缓解措施
- 缓解措施应具体可执行，不是泛泛而谈

### 8.13 未来扩展

- 列出当前版本不实现但未来可能需要的能力
- 标注优先级（P2/P3），不使用 P0/P1（那些应在实现计划中）

### 8.14 相关文档

- 使用相对路径链接
- 至少包含：相关特性文档、产品规划总览、主要代码库
- 链接格式：`[显示文本](相对路径) - 说明`

## 九、格式规范

### 9.1 Markdown 格式

- 标题层级：`#` 特性名称 → `##` 章节 → `###` 小节 → `####` 子小节
- **章节编号使用阿拉伯数字（1, 2, 3...），不使用中文数字（一、二、三...）**
- **代码块可用于 ASCII 图表**（架构图、ER 图、流程图等），不用于展示 JSON/SQL/代码示例

### 9.4 粗体格式规范

粗体（`**text**`）是 Markdown 中常用的强调手段，但使用不当会导致渲染异常或语义混乱。编写或更新 Markdown 文档后，**必须执行以下粗体格式检查**：

#### 检查项

| 编号 | 检查项 | 错误示例 | 正确示例 | 说明 |
|:----:|--------|----------|----------|------|
| B1 | 粗体内不得包含句末中文标点 | `**AI 覆盖了多少环节？**` | `**AI 覆盖了多少环节**` | `？`、`。`、`！` 等句末标点应移出粗体标记 |
| B2 | 粗体不得包裹完整的长句或问句 | `**如何证明 AI 真正在起作用**` | `**如何证明 AI 真正在起作用**——即如何用数据回答"AI 有没有效"` | 粗体应仅强调关键术语或短语，不应包裹整句 |
| B3 | 粗体标记与中文字符之间不得有多余空格 | `** 覆盖广度 **` | `**覆盖广度**` | `**` 紧贴内容，不加空格 |
| B4 | 粗体内中文与英文/数字之间保留空格 | `**AI化场景**` | `**AI化场景**` | 中文术语可紧凑；如为独立英文词则保留空格：`**AI 化场景**` |
| B5 | 表格单元格中的粗体标签应简洁 | `**覆盖广度核心指标**：平台级 AI化场景总量` | `**覆盖广度核心指标**：平台级 AI化场景总量` | 表格内的粗体用于标签/分类，冒号放在粗体外 |

#### 检查流程

编写或更新任何 Markdown 文档后，AI 必须执行以下自动检查：

1. **扫描所有 `**...**` 模式**，识别粗体内容
2. **逐项检查 B1-B5**：
   - B1：正则 `/\*\*[^*]*[？！。！]\*\*/` 匹配则报错
   - B2：粗体内容超过 15 个字符且为完整句子（含主谓结构）则警告
   - B3：正则 `/\*\* [\u4e00-\u9fff]|[\u4e00-\u9fff] \*\*/` 匹配则报错
   - B4/B5：人工语义判断
3. **自动修复**：对 B1、B3 类错误直接修复；对 B2 类问题缩小粗体范围至关键术语
4. **报告修复结果**：列出所有修复项，如无问题则说明"粗体格式检查通过"

### 9.5 目录格式规范

特性文档的"目录"章节**必须使用可点击的缩进 Markdown 列表格式**，禁止使用表格格式。

**格式要求**：

1. **可点击链接**：每个章节条目使用 `[标题](#锚点)` 格式，确保目录条目可直接跳转
2. **缩进层级**：
   - 一级章节（`##`）：无缩进，使用 `- ` 前缀
   - 二级小节（`###`）：2 空格缩进，使用 `  - ` 前缀
   - 三级子小节（`####`）：4 空格缩进，使用 `    - ` 前缀
3. **扩展描述标题**：在章节编号和标题后，使用破折号 `—` 追加描述性说明，帮助读者通过目录了解章节内容
4. **锚点格式**：使用 GitHub 风格锚点（小写、连字符替换空格、去除标点），确保链接可正确跳转

**格式示例**：

```markdown
## 目录

- [1. 功能概述 — 目标、范围与核心价值](#1-功能概述)
  - 核心价值
- [2. 完成规范 (DoD) — 按分类组织的验收标准](#2-完成规范-dod)
  - [2.1 核心功能](#21-核心功能)
  - [2.2 数据一致性](#22-数据一致性)
- [6. 系统架构 — 架构图与变更摘要](#6-系统架构)
  - [6.1 架构图标题](#61-架构图标题)
  - [6.2 模块变更摘要](#62-模块变更摘要)
    - [6.2.1 子小节](#621-子小节)
```

**禁止格式**：

| 禁止内容 | 原因 |
|----------|------|
| 表格格式目录（`| 章节 | 标题 |`） | 不可点击跳转，信息密度低 |
| 纯文本目录（无链接） | 无法直接跳转到对应章节 |
| 无缩进的平铺列表 | 无法体现文档层级结构 |
