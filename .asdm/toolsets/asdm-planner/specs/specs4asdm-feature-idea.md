# specs4asdm-feature-idea

本文档定义了 `asdm-feature-idea` action 的专属规范，补充共享规范中的通用规则。

## 定位与边界

### 适用场景

`asdm-feature-idea` 适用于**早期想法捕捉**，不适用于正式特性规划。当团队产生新特性想法但尚未进入正式规划流程时，用最轻量的方式记录想法、分配编号、创建初始文档。

### 不执行的操作

| 禁止操作 | 原因 |
|----------|------|
| 代码扫描 | 想法阶段无需分析现有代码 |
| 调研总结文件 | 代码扫描的产出，无扫描则无调研 |
| 完整特性文档 | 仅编写概述部分，完整文档由 planning action 完成 |
| 修改已有特性文档 | 仅创建新特性，不修改已有特性 |

### 与其他 action 的衔接

```
想法阶段 → /asdm-feature-idea（本 action）
    ↓
轻量规划 → /asdm-feature-planning-lite（6 章精简文档 + 代码扫描）
    ↓ 或
完整规划 → /asdm-feature-planning（14 章完整文档 + 代码扫描）
```

## 文档版本与状态规则

### 版本号

- 想法阶段文档版本从 **0.1** 开始（非 1.0）
- 后续通过 `/asdm-feature-planning-lite` 或 `/asdm-feature-planning` 升级到 1.0 时，表示进入正式规划

### 文档状态标记

| 阶段 | 文档状态 | 文档版本 |
|------|----------|----------|
| 想法记录 | 💡 想法记录 | 0.1 |
| 轻量规划 | 📝 规划中 | 1.0+ |
| 完整规划 | 📝 规划中 | 1.0+ |

### 修订记录

想法阶段的修订记录内容固定为"初始想法记录"，不要求详细说明。

## 语义分析规则

### 分析范围

由于不执行代码扫描，语义分析是 idea action 的核心分析手段，需覆盖：

1. **核心问题识别**：用户想要解决什么问题？
2. **价值归纳**：这个特性能带来什么价值？
3. **范围界定**：特性的影响范围大致覆盖哪些模块和功能？
4. **关联发现**：与现有特性的关联和依赖关系
5. **模糊点识别**：用户描述中存在哪些不清晰、不完整或潜在歧义的地方

### 语义分析约束

- **基于用户输入推断**，不基于代码分析
- **变更范围允许模糊**：标注"基于语义分析推断"即可，不要求精确
- **核心价值通常归纳 2-3 条**：从用户思路中提炼，不超过 5 条
- **不确定时标注**：对无法确定的内容标注"待确认"，而非猜测

## 待澄清问题规则

### 问题生成维度

| 维度 | 说明 | 示例 |
|------|------|------|
| 目标明确性 | 特性要解决的核心问题是否清晰 | "主要解决实时推送还是定期汇总？" |
| 范围边界 | 特性的影响范围和边界是否明确 | "是否包含系统告警？还是仅限协作消息？" |
| 用户角色 | 目标用户和使用场景是否清晰 | "面向所有用户还是仅管理员？" |
| 数据来源 | 特性涉及的数据来源和类型 | "通知数据分别来自哪些模块？" |
| 交互方式 | 用户与特性的交互方式 | "站内信、弹窗、还是邮件推送？" |
| 依赖关系 | 与其他特性的关联是否明确 | "是否需要与 FT-003 集成？" |
| 技术约束 | 是否有特殊的技术要求或限制 | "是否有实时性要求？是否支持离线消息？" |

### 问题生成规则

- 问题数量控制在 **3-7 个**，聚焦最关键的澄清点
- 每个问题必须具体、可回答，避免过于宽泛
- 问题按重要性排序：目标/范围 > 用户角色 > 数据/交互 > 依赖/约束
- 对于用户描述中已明确的内容，不再生成澄清问题
- 编号格式：`Q1, Q2, Q3, ...`
- 每个问题标注所属维度

### 问题状态

| 状态 | 标记 | 说明 |
|------|:----:|------|
| 待澄清 | 🔲 | 初始状态，等待用户回答 |
| 已澄清 | ✅ | 用户已回答，回答摘要已写入"澄清记录"列 |

### 澄清交互规则

1. **逐一引导**：用户每回答一个问题，AI 立即处理并更新文档
2. **批量回答**：用户一次性回答多个问题时，批量更新
3. **跳过处理**：用户表示暂不回答时，保留问题为待澄清状态，不强制追问
4. **衍生问题**：用户回答引入新模糊点时，可追加问题（不超过 2 个），编号继续递增
5. **文档更新**：每次澄清后使用 `replace_in_file` 更新文档中的问题状态和澄清记录
6. **版本递增**：每次澄清更新文档时，修订记录版本号递增 0.0.1

## 概述章节编写规则

### 概述结构

想法文档的概述部分包含以下固定结构：

```markdown
## 1. 特性概述

{2-3 句话描述特性的目标、范围和价值}

### 核心价值

- **{关键词}**：{说明}
- **{关键词}**：{说明}

### 归属模块

| 属性 | 值 |
|------|-----|
| **模块编号** | {module} |
| **模块名称** | {从 ASDM-ProductPlanning.md 读取} |
| **优先级** | {priority} |
| **目标 Release** | {release 或 "待定"} |
| **依赖特性** | {depends 或 "无"} |

### 变更范围

| 变更模块 | 变更内容 | 影响范围 |
|----------|----------|----------|
| {模块名称} | {基于语义分析推断} | {影响说明} |

### 待澄清问题

> 以下问题基于当前想法描述中的模糊点生成，请在后续对话中逐一澄清。澄清后文档将自动更新。

| 编号 | 问题 | 维度 | 状态 |
|:----:|------|------|:----:|
| Q1 | {基于语义分析生成的第1个问题} | {维度} | 🔲 待澄清 |
| Q2 | {基于语义分析生成的第2个问题} | {维度} | 🔲 待澄清 |
| Q3 | {基于语义分析生成的第3个问题} | {维度} | 🔲 待澄清 |
```

### 编写要点

- 概述描述基于语义分析整理，不基于代码扫描
- 核心价值从用户思路中提炼，每条以关键词加粗开头
- 变更范围允许模糊描述，但应覆盖用户提及的关键领域
- 归属模块信息从 `ASDM-ProductPlanning.md` 模块清单读取，确保编号和名称对应
- 待澄清问题基于语义分析的模糊点生成，初始状态均为 🔲 待澄清

## 特性列表插入规则

### 插入位置

新特性条目必须插入到 `ASDM-ProductPlanning.md` 的**特性列表2 - 规划中**的**顶部**（表头之后的第一行）。

### 插入原因

- 新想法放在最前面，便于团队快速看到最新记录
- 与正式规划文档的尾部追加不同（正式规划按编号顺序）
- 想法阶段条目后续进入正式规划时，可调整到合适位置

### 条目格式

```markdown
| FT-XXX | [{特性名称}](./Feat/FT-XXX-{name}/FT-XXX-{name}-idea.md) | {priority} | 🔵 规划中 | {特性说明} |
```

> **注意**：想法阶段链接指向 `-idea.md` 文件。后续进入正式规划生成 `-Feature.md` 文档后，需将链接更新为指向 `-Feature.md`。

### 特性说明要求

特性说明列应简明扼要，通常从用户描述中提炼，不超过 50 字。

## 参数提取规则

### 特性名称提取

- 从描述中提取核心概念，归纳为 2-20 字符的简短名称
- 名称应具有辨识度，避免过于笼统（如"新功能"）
- 若用户描述过于模糊，向用户确认名称

### 模块映射

常见模块名称关键词映射（完整映射以 `ASDM-ProductPlanning.md` 模块清单为准）：

| 关键词 | 可能的模块编号 |
|--------|---------------|
| 认证、用户、登录、权限 | 1 |
| 组织、团队、成员 | 2 |
| 项目、空间 | 3 |
| 资源库、代码库、Git | 4 |
| 工作项、任务、需求、Bug | 5 |
| 迭代、看板、进度 | 6 |
| CI/CD、流水线、构建 | 7 |
| 测试、用例 | 8 |
| 制品、包、仓库 | 9 |
| 代码、评审、合并 | 10 |
| 知识库、文档、Wiki | 11 |
| AI、智能 | 12 |
| MCP、插件、扩展 | 13 |
| 部署、运维 | 14 |

### 优先级映射

| 用户表达 | 映射 |
|----------|------|
| "高优先级"、"紧急"、"必须"、"P1" | P1 |
| "中优先级"、"一般"、"正常"、"P2" | P2 |
| "低优先级"、"不急"、"可以延后"、"P3" | P3 |
| 未指定 | P2（默认） |

## 路径约束

### 根路径

所有路径相对于工作区根目录：
```
/home/azureuser/source/asdm-product-management/
```

### 特性文档路径

| 类型 | 路径 |
|------|------|
| 目录 | `docs/planning/Feat/FT-XXX-{特性名称}/` |
| 想法文档 | `docs/planning/Feat/FT-XXX-{特性名称}/FT-XXX-{特性名称}-idea.md` |

> **注意**：想法阶段文档使用 `-idea.md` 后缀，标题格式为 `# FT-XXX {特性名称}（想法）`。后续通过 `/asdm-feature-planning-lite` 或 `/asdm-feature-planning` 进入正式规划时，生成 `-Feature.md` 后缀的正式文档。

### 产品规划文档

```
docs/planning/ASDM-ProductPlanning.md
```

## 校验规则

### 特性编号格式

- 必须匹配 `FT-\d{3}` 格式
- 编号顺序递增，自动跳过已使用的编号

### 特性名称唯一性

- 新特性名称不得与 `ASDM-ProductPlanning.md` 中已有特性重复
- 检查范围包括三个特性列表（设计中/实现中、规划中、已实现/已废弃）

### 依赖特性校验

- 依赖的特性编号必须已存在于 `ASDM-ProductPlanning.md` 特性清单中
- 被依赖的特性不得为"已废弃"状态

## 错误处理

### 模块编号无效

1. 向用户展示有效的模块清单
2. 请求用户选择正确的模块编号

### 特性名称重复

1. 提示用户名称已存在，显示已有特性的编号和状态
2. 建议用户修改名称或确认是否要更新已有特性

### 缺失必填参数

1. 一次性列出所有缺失项
2. 提供模块清单供用户选择
3. 不使用默认值填充必填参数

## 与其他 Action 的关系

### 与 asdm-feature-planning-lite

- idea 创建初始想法文档后，可通过 planning-lite 升级为 6 章精简文档
- planning-lite 会执行代码扫描，补充现有代码分析章节
- 文档版本从 0.1 升级到 1.0

### 与 asdm-feature-planning

- idea 创建初始想法文档后，可通过 planning 升级为 14 章完整文档
- planning 会执行完整的两阶段代码扫描
- 文档版本从 0.1 升级到 1.0

### 执行顺序

```
/asdm-feature-idea → 记录想法（v0.1，仅概述）
    ↓
/asdm-feature-planning-lite 或 /asdm-feature-planning → 正式规划（v1.0+，完整文档）
    ↓
/asdm-feature-review → 审查文档完整性和一致性
    ↓
/asdm-feature-progress → 跟踪实现进展
```
